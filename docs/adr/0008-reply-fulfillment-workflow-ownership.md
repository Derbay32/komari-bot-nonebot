# 回复履约由深工作流统一拥有并以正交事实持久化

回复送达后的状态迁移、租约、重试、幂等承诺与清理曾分散在插件入口、`MessageHandler` 和 Repository adapter，调用方必须共同掌握状态名与调用顺序。我们决定由 `komari_chat` 内部的回复履约工作流统一拥有从持久准备、平台发送结果登记到全部送达后承诺完成的生命周期；插件入口只发起一次履约调用，管理端只经插件顶层运维 seam 对账或续跑，Repository 退回纯存储 adapter。

回复履约不再用单一状态枚举混合送达事实、worker 占有和业务结局。持久化采用父子结构：父记录保存不可变履约身份、送达事实与单一执行租约，子记录按固定领域集合保存各项适用承诺的独立进度、重试与必要载荷；整体状态由这些正交事实派生。承诺集合在首次准备时冻结，单项失败不阻塞其他承诺，只有全部适用承诺完成时履约才完成。

## Considered Options

- **保留现有宽 Repository interface，仅增加 facade**：被拒绝——插件入口和 Handler 仍需掌握准备、送达、领取、心跳、退避与清理顺序，无法通过 deletion test，module 仍然 shallow。
- **继续扩展单一状态宽表**：被拒绝——送达事实、租约与四项独立承诺会形成大量组合状态和重复列，无法自然表达单项待重试、待处置与逐项清除载荷。
- **用 JSONB 保存完整承诺状态机**：被拒绝——会把状态约束、领取查询和原子更新退回应用层；本项目只把 JSONB 用作灵活载荷，不用作状态机真源。
- **建设通用 outbox 引擎或开放动态承诺注册**：被拒绝——当前只有回复履约这一具体领域和固定承诺集合，没有第二个同构变体；通用协议会把幂等、隐私和失败语义重新泄漏给调用方。

## Consequences

- 正常聊天、后台恢复和管理运维共享同一个回复履约 interface；调用方与测试不再直接断言内部状态迁移、owner token 或 Repository 调用序列。
- 每项送达后承诺独立分类错误、计算退避并保留幂等证据；父级租约保证同一回复履约同一时刻只有一个执行者。
- 待确认回复与待处置回复必须经受审计的运维操作解决，且不得通过重新发送、修改冻结载荷或跳过承诺来伪造完成。
- 旧宽表到父子模型采用停机原子迁移，不保留双写、旧状态兼容或运行时 fallback；历史事实不足以安全转换时迁移必须 fail fast。
- 主动回复预占的生成期生命周期不并入本决定；回复履约只消费其确认与释放能力，候选三继续独立设计和实施。
